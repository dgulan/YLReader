# amd64 worker 合成资源与性能结果

对应 sandbox-worker-performance-design-2026-11-14.md。第一轮仅新增显式启用的 integration 性能测试和复现脚本；第二轮修改了 sandbox 生产执行路径（父进程在途字节预算），未改变默认执行模式、API/DDL、错误枚举、资源限制或备份格式。未部署、提交、推送、合并；没有读取 references 或生产数据。

## 证据与方法

完整记录 `.toolchain/worker-performance-695d4ac04ba0/result.json`，各阶段stdout/stderr和OOM事件同目录。固定worker镜像ID `sha256:c8138b9ad87ee9f48c3b163518a81a5da12f1ec05614302431cb352867b7d78e`。Docker Desktop29.9.3、x86_64、Linux6.18.58.1-microsoft-standard-WSL2，虚拟机4CPU、约3.82GiB内存。不是ARM设备或NAS实测。

同一Go1.26.11工具链构建无race的测试可执行文件，测试进程限制1CPU/512MiB；每个worker独立1CPU/128MiB、无额外swap、pids64、非root、只读、无网络。两轮顺序执行local、单worker、四worker；每种模式6个工作负载×并发1/4/16，每组预热8次、计量100次。固定顺序、短样本和CPU配额会影响结果；不同模式的总CPU预算不同，不推导加速比或生产SLA。

指标包括成功延迟p50/p95/p99、全部调用p95、成功/总吞吐、错误分类、父进程分配字节及GC次数。分位数采用nearest rank，吞吐按整组墙钟时间计算。HTTP为20ms合成适配器，不包含真实网络、DNS或书源解析链；正文为ASCII合成输入，不代表中文/转义密集文本或真实长时阅读。

## 内存与输入边界

通过独立非root、无额外capability的只读观察容器，读取worker根命名空间中的cgroup memory.peak。它是该cgroup生命周期内总内存高水位，包含缓存等，既不是单请求峰值，也不是纯Go堆或RSS；worker重启后不沿用旧cgroup峰值。观察进程不进入worker的cgroup。父进程直接读取自身同一指标。

正常阶段均无OOM、无worker重启。单worker正常阶段高水位两轮16.1/28.0MiB；四worker各自15.8–20.0MiB，父测试进程29.6–30.6MiB。各容器峰值不同步，不能相加冒充同一时刻的整组峰值。进程内父容器约24.3MiB，单worker模式父容器约26.7–26.8MiB。

每个remote配置每轮单独请求4/8/16/31/32MiB输入，各一次，不自动重试原调用。四组中4/8/16MiB均正确返回；31MiB均失败，并分别观察到一次OOM事件、一次worker重启；32MiB因输入总预算包含键等开销而被拒绝。每次边界调用之后，新的探测及独立调用均恢复。只证明这些样本单次执行，不能宣称所有16MiB内容都可接受。

边界阶段父容器高水位206.3–221.6MiB（第一轮；第二轮为216.1–232.6MiB），说明worker的128MiB限制不覆盖父进程输入及IPC编码开销。第一轮尚未测试多份近上限输入同时进入父进程，因此当时不能宣称父进程已有总在途字节硬上限；该缺口已由下节的在途字节预算补上。worker重启后的峰值也不能冒充被OOM杀死进程的历史峰值。

## 在途字节预算复核（第二轮）

针对上一节“暂无父进程在途字节硬上限”，本轮在父进程引入 IPC 准入预算，并给脚本增加第三阶段 `admission`：

- 每次求值按输入的 JSON 编码上界计费，成本系数 2（copyVars 与编码缓冲可能并存）；默认预算为 2×输入上限（生产 64MiB）。预算与执行槽共用 250ms 准入窗口，饱和返回既有 `ErrSandboxTimeout`（HTTP 504），不无界排队、不截断输入。
- 预算等待使用独立计时窗口，验证大输入本身耗时不再吃掉准入预算；总准入等待上界为 2×QueueTimeout。
- 脚本在 edge 之后重启全部 worker 再执行 admission，避免 31MiB 边界 OOM 的热堆影响；每个 admission 行记录输入尺寸、预算容量、成功/超时分类、父容器 cgroup 峰值。

用例与两轮结果（admission 阶段无新增 OOM、无重启）：

| 用例 | worker 数 | 成功/尝试 | 成功 p95 (ms) | 父容器峰值 (MiB) |
|---|---:|---:|---:|---:|
| 1MiB 转义输入，并发=worker | 1 | 1/1 | 66.1–79.5 | 24.3–25.7 |
| 1MiB 转义输入，并发=worker | 4 | 4/4 | 123.1–142.6 | 44.7–49.6 |
| 4MiB 输入 / 10MiB 紧预算 | 1 | 1/1 | 698.9–715.1 | 37.1–37.9 |
| 4MiB 输入 / 10MiB 紧预算 | 4 | 1/4（3 次 250ms 窗口超时） | 710.9–719.0 | 53.2–56.9 |
| 12MiB 输入 / 64MiB 预算 | 1 | 1/1 | 308.8–886.3 | 140.8–152.6 |
| 12MiB 输入 / 64MiB 预算 | 4 | 2/4（2 次超时） | 448.1–472.0 | 145.4–152.6 |

紧预算用例用一个 600ms 的合成 HTTP 桥接调用占住已准入的字节，四个并发调用稳定得到 1 成功 + 3 次 504；等待者在 250ms 窗口内被拒绝，没有形成串行放行。12MiB 用例在 64MiB 预算下最多同时容纳两个调用，符合 2×12MiB 的计费；两个持预算 worker 的 cgroup 峰值约 80–84MiB，未触发 OOM。

第二轮 normal 阶段共 10800 次调用：10637 成功、163 次受控超时、其他错误 0。163 次超时全部出现在单 worker、客户端并发 16 的 input-1MiB（59–60/100）、output-256KiB（87–98/100）和 http-20ms（64–69/100）；四 worker 在并发 1/4/16 下六种工作负载均 100/100。四 worker 的成功 p95 为：短规则并发 4 3.2–3.4ms、1MiB 输入并发 4 56.4–59.0ms、1MiB 输入并发 16 186.3–194.6ms、256KiB 输入并发 16 61.2–68.1ms、20ms HTTP 并发 4 27.7–27.8ms。normal 阶段父容器峰值 25.4–35.1MiB。

边界阶段仍有同一现象：4/8/16MiB 在全部 6 组 profile 中被正确接受；31MiB 每组失败一次（等待超时或规则执行失败），并伴随一次 worker OOM 与一次重启，重启前存活 worker 的峰值 116.5–118.6MiB；32MiB 在 3–8ms 内被输入预算拒绝。每次边界调用后探测均恢复。OOM 计数按 profile 起点累计，因此 edge 的 OOM 也会出现在随后 admission 的日志中，本轮 admission 本身未增加 OOM。

结论：父进程在途字节预算按设计生效，64MiB 生产默认能容纳单个最大输入，并在 12MiB 并发下把总在途控制在两个调用；128MiB worker 仍不足以承载 31MiB 逻辑输入，不能靠提高输入上限掩盖。父进程峰值随并发大输入上升，生产编排需要同时约束父进程与 worker 的内存，并按 operations 文档允许的上限（<=256MiB）评估 worker 规格。


60个自有临时对象（容器和IPC卷）均按随机标签清理，未删除既有镜像、业务容器或卷。性能工具跨两轮重复了10个父测试进程，不将它们计作此前全量回归新增10个业务用例。

测试可执行文件交叉编译及Linux目标integration标签的sandbox包go vet通过；Python脚本语法、git diff --check通过。备份65项检查、16份备份冻结摘要、主冻结表10份摘要均匹配。仅补充测试/脚本/文档，未重复声称全量后端、浏览器或生产镜像扫描已重跑。

## 资源配置与拒绝边界建议

以下为本机合成负载下的建议基线，不是生产 SLA，也不是部署批准；真实书源与长时负载仍需第 3 阶段复核。

| 角色 | 建议 | 依据 |
|---|---|---|
| API/父进程 | 1–2 vCPU、512MiB 起 | normal 峰值 25.4–35.1MiB；12MiB×2 并发 141–153MiB；31MiB 边界 216–232MiB |
| worker | 1 vCPU、256MiB、pids 64、无网络、只读、非 root | 128MiB 下 31MiB 输入 OOM；12MiB×2 时峰值 80–84MiB；256MiB 的 31MiB 边界尚未实测 |
| worker 数量 | 1–4，默认 4 槽 | 四 worker 在并发 1/4/16 的合成负载全部成功；单 worker 并发 16 受槽位与 250ms 队列限制 |
| 单次输入 | ≤32MiB 拒绝阈值，预算按 2×计费 | 4/8/16MiB 接受；31MiB 在 128MiB 下失败；32MiB 快速拒绝 |
| 在途总预算 | 默认 64MiB（2×InputLimit），与 250ms 窗口共用 | 紧预算 4MiB 稳定 1 成功 + 3×504；12MiB×4 最多 2 个在途 |
| 超时 | 脚本 3s、排队/准入 250ms、结果与转换同受监视 | 超时、队列到期与预算饱和统一 504 `sandbox_timeout` |

表中的输入上限、在途预算与并发槽当前由 `sandbox.Config` 默认值决定（`main.go` 只读取 socket 列表），没有环境变量入口；调整需要改代码并重跑本验收，不能指望部署时改参数。

拒绝边界：输入/输出超预算为 422；执行取消、超时、排队或预算饱和为 504；未知 panic 为 500。服务端不得把超限输出截断为成功，也不得因预算饱和无限等待。

## 是否把独立 worker 设为推荐配置

结论：**本轮不把独立 worker 设为默认配置，也不把它作为“推荐配置”写进部署默认值；保持显式 opt-in。** 若部署方主动选择隔离模式，按上表 1–4 worker、每 worker 1 vCPU/256MiB、父进程 1GiB（实测最低 512MiB 可用但余量小）配置，并把 `MaxConcurrent` 限制在 worker 数以内。

理由：

- 编排缺口：`docker-compose.yml` 目前没有 worker 服务、socket 卷或资源上限，默认 `YREADER_SANDBOX_SOCKETS` 为空；照现状开启只会继续走进程内 goja，写“推荐”会造成文档与事实不符。
- 无回退：ADR-021 明确启动探测失败即拒绝启动、不回退进程内模式；在没有编排与告警的情况下设为默认，会把单点配置错误放大为启动失败。
- 成本可测但未覆盖真实负载：合成负载下 worker 侧峰值 80–119MiB、父进程 25–232MiB，31MiB 输入在 128MiB 下 OOM；真实书源的长正文、转义与并发分布尚未测。
- 平台未闭环：性能数据仅 amd64；arm64 仍待真实主机复核（第 1 阶段遗留门禁）。

成为默认/推荐配置的前置条件：compose 增加 worker 服务与 socket 卷、显式 CPU/内存上限与健康检查；readyz 暴露 worker 状态并有告警；完成 ARM 原生与真实书源长时复跑；给出从进程内模式切换与回滚的操作步骤。满足后再单独评审，不在本轮直接改默认。

## 结论与下一步

两轮获得可复现的合成基线。四 worker 在并发不超过 4 时六种负载全部成功；单 worker 在并发 16 时受 4 个执行槽与 250ms 排队预算限制，1MiB/256KiB 输出/20ms HTTP 出现 59–98% 的成功率，属有意的过载拒绝而不是回归。父进程在途字节预算已按 2×输入上限落地：紧预算下 4 个并发稳定 1 成功 + 3 次 504，12MiB 并发在 64MiB 预算下最多 2 个在途，未 OOM。

保留当前隔离/超时/准入限制，不把排队超时改为无限等待，也不自动切换默认模式。128MiB worker 不能承载 31MiB 逻辑输入；生产 worker 规格仍按 operations 文档的 <=256MiB 评估，并同时约束父进程内存。

下一步用真实合法书源、中文长正文和较长运行时间验证延迟与内存稳定性，再制定生产配置；ARM 原生运行门禁、真实阅读验收、备份恢复生产闭环及发布门禁继续保留。

## 复现

在backend模块用Go1.26.11设置GOOS=linux、GOARCH=amd64、CGO_ENABLED=0，执行：

```text
go test -c -tags integration -o ../.toolchain/worker-perf-test-linux ./internal/engine/sandbox
```

回到项目根目录，使用已存在的可信本地镜像：

```text
python scripts/verify-sandbox-worker-performance.py --image yreader-pre-release:race --worker-image ylreader-worker-check:amd64-20261114 --binary .toolchain/worker-perf-test-linux
```

脚本不拉取镜像，不接触Docker socket到测试进程，不触碰持久业务数据。脚本对 worker 数大于 0 的 profile 依次执行 normal、edge、admission 三个阶段；admission 前会重启 worker 以排除边界阶段的热堆。测试默认不会启用性能模式，需要显式 `TEST_WORKER_PERFORMANCE`；边界与准入阶段还分别需要 `TEST_WORKER_EDGES=1`、`TEST_WORKER_ADMISSION=1`。父测试二进制摘要、运行镜像 ID、宿主信息、错误分类、各 cgroup 原始峰值及按 profile 起点累计的 OOM 事件均记录在 result.json 与同目录 stdout/oom-events 中。本轮证据目录 `.toolchain/worker-performance-5e4f026ea434/`。

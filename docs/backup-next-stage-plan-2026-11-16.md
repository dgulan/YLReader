## 建议的实现顺序

1. **正式交接报告契约**：明确版本、不可变绑定、检查集合、证据新鲜度、CAS登记及确认丢失规则。绑定现有operation/plan/package/manifest/target/publication，报告不含DSN、密钥、凭据、正文或宿主敏感路径；不直接将外部JSON“检查通过”转换成执行凭证。
2. **目标配置与缓存身份核验**：复核实际目标schema/账本、角色/权限、已发布对象根、header keyring引用、新JWT配置和隔离Redis身份。文件位置不等于物理目标身份；恢复前验证缓存隔离不能使用FLUSH。不能仅因实验账号能登录就认定所有真实目标配置正确。
3. **只读CLI优先**：将已存在的inspect、plan和状态诊断接入独立命令，严格区分预览与执行。错误/取消/unknown只输出可核对状态，不自动接管、重试写入或删除保留对象。
4. **受控执行与报告登记**：在契约确认后接入已有守卫链，重验计划有效期和排他能力，先在明确隔离的合成目标验证成功与失败窗口。报告持久确认前不能推进ready_for_cutover；completed的既有语义仍是隔离验证及交接完成，不等于生产流量切换。
5. **用户闭环**：将命令输出、恢复预览、冲突拒绝、失败处理和实际交接说明连成可复核操作；公开API/界面若需扩展，另行修订并冻结契约，不偷偷增加现有43操作之外的入口。

## 写代码前必须确定的具体问题

- 正式环境行为验证如何取得操作员授权与凭据，又不修改恢复用户密码、创建隐含管理员或把凭据写入报告？现有合成HTTP账号不能替代这一设计。
- 报告哪些检查可在不启动服务的情况下完成，哪些需要短时本机验证？报告有效期及目标发生变化后如何失效？不可把常驻启动或部署隐含在验证步骤内。
- Redis身份、JWT与keyring配置怎样与真实目标绑定？需要的只读权限不足时应拒绝，不能自动扩大权限。
- 报告写入或状态CAS结果未知时如何核对？继续沿用保留原则，不把已提交数据库的对象失败描述为完整回滚。
- Linux安全文件驱动已在tmpfs验证；真实NAS文件系统、S3和Windows能力不足如何明确拒绝或另验？首发范围决策不能取消宪章的最终交付要求。
